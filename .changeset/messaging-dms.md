**Direct messages (new `dms` module).** One-to-one conversations on the messaging core, with the group chat's screen: text, one image, replies, likes, edits, deletes, on-demand translation, typing, report and block. A member starts one from a profile, a "new message" picker on the Messages page, or a post, comment or message menu (`dms.entryPoints`). With `dms.firstMessage: "requests"` a first message waits in the recipient's Requests (Accept / Decline / Block and report, the sender's context shown, nothing read until accepted); a decline is silent and the sender may keep writing, but the recipient never sees a declined request's messages again, and after `declineCooldownDays` the next message starts a new request. "Seen" under my last message with `dms.readReceipts` (never on a request). A member can turn DMs off in the profile edit sheet (that blocks new DMs only). Blocks apply to DMs: a blocked pair never reaches each other and neither side reads the DM's history; admins can't be blocked out, as in the feed.

Pushes (push module): a DM message pushes the other member, a new request pushes once with a neutral line that names no one, and `messaging.pushPreview: "none"` now also drops the sender's name from a DM push's title. The member-wide switch is `notify_dms`. The center gets "your message request was accepted". Only the two members read a DM: the dashboard reads a message only through `admin_message_context`, for a reported or AI-hidden one. `messaging.onAccountDelete: "eraseDms"` and profile merge cover DMs (two DMs with one member become one). Everything is off unless the app sets `modules.dms`: an app that doesn't gets the same behaviour as before.

- **Config:** `modules.dms` (`firstMessage`, `entryPoints`, `readReceipts`, `requireAccount`, `requestsPerDay`, `declineCooldownDays`; defaults `"direct"`, `["profile"]`, `false`, `false`, `5`, `30`). `messaging.*` now also applies with only `dms` on (`messagingSettings(cfg)` is non-null with groups or dms). `dms.requireAccount` needs a linked account on both sides and calls `host.onAccountRequired("dm")`. The backend enforces its own copy (`messaging_set_settings`: `dmsFirstMessage`, `dmsReadReceipts`, `dmsRequireAccount`, `dmsRequestsPerDay`, `dmsDeclineCooldownDays`): keep both equal (dev builds warn).
- **Screens:** `MessagesScreen` gets the Conversations tab (Requests row, my DMs) and the pencil that opens the member picker, with an optional `onOpenRequests` (without it Requests opens inside the screen); new `RequestsScreen` (`onOpenRequest`, `onBack`); `ConversationScreen` serves DMs; the `"dms"` header item (the Messages page on its Conversations tab, with the unread badge); `ProfileScreen` and `ThreadSheet` take `onOpenMessages` (no "Message" without it).
- **Type changes that can break host code:**
  - `NotificationInboxScreen.onOpenMessages` now receives `{ groupId, preview? } | { conversationId }` (the DM of an accepted request): a callback typed for the group target only no longer type-checks. The feed's own `onOpenMessages` already took `conversationId`.
  - New optional `onOpenMessages?: (target: { conversationId: string }) => void` on `ProfileScreen` and `ThreadSheet`; the feed's callback fits.
  - `FeedHeaderItem` gains `"dms"`. The `resolveHeaderZones` util (not exported from the package index) takes a required `groups` flag and a `dms` flag: a dms-only app no longer shows a `"groups"` header item. With `homeLayout: "segmented"`, put `"dms"` in the header, not `"groups"`.
  - `AvatarPlacement` gains `"dm"` and `"dmHeader"` (a custom `renderAvatar` switching on it).
  - `InboxItem.kind` gains `"dm_request_accepted"`; `NOTIFICATION_PREFERENCE_KEYS` gains `notify_dms` (read and written only with `modules.dms` on, optional on `NotificationPreferences`).
  - The "Feed | Groups" selector is now the shared `SegmentedTabs`: its padding scales with a custom `theme.spacing` (identical at the default unit).
  - `COMMUNITY_EVENTS` gains `dmStarted`, `dmRequestAccepted`, `dmRequestDeclined`, `dmRequestBlocked` (ids only).
- **Android:** the post and comment "…" menus open as a sheet (every action, a Cancel row, closed by back or a tap outside): the system alert showed three buttons at most and dropped Cancel once "Message" was added. iOS and web keep the system alert.
- **Core exports:** `useStartDm`, `useDmRequests`, `useAcceptRequest`, `useDeclineRequest`, `useBlockAndReportRequest`, `useAcceptsDms`, `useSetAcceptsDms`, `usePeerRead`, `useMemberSearch`, `useDmFlags`, `dmFlagQueryOptions`, `dmsSettings`, and the `DmsConfig` / `DmsEntryPoint` / `DmSource` types.
- **CLI:** new module `dms` (implies `messaging`; `init` without `--modules` installs it too, the app shows nothing until it sets `modules.dms`). Migrations `dms/001`–`005` (`005`: a request counts against `requestsPerDay` when sent; each member's private channel `dms:<id>` keeps the Requests row, the list and the badge live), no new function (`notify-message`, `report-to-slack` and `account-delete` handle DMs). `npx @rocapine/community upgrade --add-modules dms`, `supabase db push`, `messaging_set_settings` for the `dms*` keys, then `supabase functions deploy`. Traps: a host that adds `push` after `dms` re-runs `messaging/002` then `dms/002`; one that adds `groups` after `dms` re-applies `dms/001` (`upgrade` copies it again); a DM-only install has no storage sweep for erased images (it comes with `groups/005`). See `docs/backend-runbook.md`, section 8, and `docs/integration.md`, Direct messages.
